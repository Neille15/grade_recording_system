# Pedagoclick ASP.NET Core integration plan

## Target architecture

- **Frontend:** the existing React/Vite app in `src/`, converted from in-memory seed state to an API client.
- **Backend:** ASP.NET Core Web API on .NET 8 or newer, using controllers, DTOs, FluentValidation, JWT bearer authentication, and Swagger/OpenAPI.
- **Database:** SQL Server, created by [`database/01_create_pedagoclick.sql`](../database/01_create_pedagoclick.sql).
- **Persistence:** EF Core database-first. The database is authoritative; generated entity classes are not hand-edited.
- **Offline grading:** IndexedDB stores an outbox of score mutations. The API uses optimistic concurrency (`rowversion`) and returns conflicts instead of silently overwriting newer scores.

## Delivery phases

1. **Create the database**
   - Run the SQL script in SQL Server.
   - Replace the demo users' `PasswordHash` values with hashes generated by ASP.NET Core Identity or the chosen identity provider.
   - Add quarter rows if quarter metadata is needed beyond the `Quarter` column.
2. **Scaffold the backend**
   - Create `Pedagoclick.Api` with `dotnet new webapi`.
   - Install `Microsoft.EntityFrameworkCore.SqlServer`, `Microsoft.EntityFrameworkCore.Design`, `Microsoft.AspNetCore.Authentication.JwtBearer`, and validation/OpenAPI packages.
   - Scaffold `PedagoclickDbContext` and entities from the live database.
   - Keep connection strings and JWT signing keys in user secrets/environment variables, never in source control.
3. **Implement authentication and authorization**
   - `POST /api/auth/login` returns a short-lived access token and refresh-token strategy.
   - Map `teacher`, `adviser`, and `admin` claims to policies.
   - Enforce assignment ownership in the API, not only in the UI:
     teacher/adviser may edit scores only for active `ClassAssignments`;
     advisers may manage enrollments for their advised section;
     admins manage users, assignments, school years, and audit views.
4. **Implement read APIs**
   - Return a dashboard bootstrap payload so the frontend does not make many sequential requests.
   - Filter every query by the authenticated user's role and active school year.
5. **Implement writes and audit**
   - Validate score ranges against the selected `AssessmentItem.MaxScore`.
   - Save a complete score batch in a transaction.
   - Require the last-known `rowversion`; return `409 Conflict` with current values when it changed.
   - Write one audit row for roster, assignment, assessment-structure, score, collaboration, and account changes.
6. **Connect the frontend**
   - Add `VITE_API_BASE_URL`.
   - Replace login's demo role selection with `/api/auth/login`.
   - Add typed API functions and loading/error states.
   - Replace local `students`, `recs`, `saved`, `msgs`, `audit`, and admin lists with query results.
   - Keep the current score calculation in a shared TypeScript domain module until reports are verified against backend results.
7. **Offline and sync**
   - On score save, immediately write the mutation to IndexedDB when offline.
   - On reconnect, send idempotent batches with `clientMutationId`, base row versions, and scores.
   - Display server conflicts in the existing Sync & audit view and let the user choose reload or retry.
8. **Test and deploy**
   - Unit-test authorization, grade calculation, score validation, and conflict handling.
   - Integration-test every endpoint against SQL Server.
   - Add frontend API-mocking tests for loading, 401, 403, 409, offline, and retry states.
   - Configure CORS only for the deployed frontend origin, HTTPS, structured logging, health checks, backups, and migrations/schema-change review.

## API contract

### Authentication

| Method | Route | Purpose |
|---|---|---|
| POST | `/api/auth/login` | Authenticate email/password; return access token and user summary |
| POST | `/api/auth/refresh` | Rotate refresh token |
| GET | `/api/auth/me` | Return current user, roles, and permissions |

### Reference and dashboard data

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/bootstrap?schoolYearId=1` | Current user, school years, assignments, unread threads, and pending sync count |
| GET | `/api/school-years` | List school years |
| GET | `/api/classes?schoolYearId=1` | Classes visible to the current user |
| GET | `/api/classes/{classId}/roster` | Enrolled learners |
| GET | `/api/classes/{classId}/gradebook?quarter=2` | Assessment structure, scores, calculated status, and row versions |

### Gradebook and roster writes

| Method | Route | Purpose |
|---|---|---|
| PUT | `/api/classes/{classId}/gradebook/structure` | Add/remove assessment items and change max scores |
| PUT | `/api/classes/{classId}/gradebook/scores` | Transactional score batch save with concurrency tokens |
| POST | `/api/classes/{classId}/roster` | Add learner/enrollment (adviser policy) |
| PATCH | `/api/learners/{learnerId}` | Correct learner name (adviser policy) |
| DELETE | `/api/classes/{classId}/roster/{learnerId}` | Deactivate enrollment, retaining audit history |

### Collaboration, reporting, and administration

| Method | Route | Purpose |
|---|---|---|
| GET/POST | `/api/collaboration/threads` | List or create addressed teacher threads |
| POST | `/api/collaboration/threads/{threadId}/replies` | Reply to a visible thread |
| PATCH | `/api/collaboration/threads/{threadId}` | Resolve a thread |
| GET | `/api/reports/progress?classId=&quarter=` | Report-ready progress data |
| GET/POST/PATCH | `/api/admin/users` | Admin account management |
| GET/POST/PATCH | `/api/admin/assignments` | Admin class-teacher assignments |
| GET | `/api/admin/audit-logs` | Filtered audit log |

## DTO and security rules

- Never expose `PasswordHash`, refresh tokens, or unrestricted user records.
- Use DTOs rather than returning scaffolded EF entities directly.
- All IDs are server-generated; all timestamps are UTC.
- `PUT /scores` accepts `{ enrollmentId, assessmentItemId, score, baseRowVersion }[]` and returns per-row status.
- A missing score is `null`; zero is a valid score. The API rejects negative scores and scores above `MaxScore`.
- Use soft deactivation (`IsActive`) for users, learners, enrollments, assignments, and scores where history matters.
- Add rate limiting to login and standard `ProblemDetails` responses for validation, authorization, not-found, and concurrency errors.

## Frontend migration order

1. Introduce `src/api/client.ts` with token handling and typed `fetch` helpers.
2. Add `src/api/types.ts` matching the DTOs above.
3. Change login and bootstrap loading first.
4. Change Encode grades and Sync & audit next because they require concurrency/offline behavior.
5. Change Advisory, Collaboration, Reports, and admin views.
6. Remove demo constants and local state only after each screen has an API-backed loading, empty, error, and retry state.

## Acceptance criteria

- A teacher cannot read or mutate another teacher's gradebook by changing a URL or request body.
- An adviser can manage only enrollments in their own advised class.
- Two users editing the same score receive a visible conflict; the later request cannot overwrite silently.
- Refreshing the browser preserves server data; offline score edits survive reload and sync after reconnection.
- All mutations create an audit record with actor, action, entity, timestamp, and useful detail.
- Existing grade calculations and report output match the current seeded UI for all complete and incomplete learners.
